# Authentication and Public Provider Profiles — Design

**Date:** 2026-09-27  
**Status:** Proposed design; awaiting user review.  
**Scope:** Frontend login and registration, role-aware account/profile APIs, company-driver invitations, and public company/independent-driver profiles. Didit identity verification is explicitly excluded.

## 1. Goals and non-goals

Provide email/password registration with required email confirmation, password login followed by SMS phone MFA, and a shared public profile experience for companies and independent drivers. Company-linked drivers join only through an owner-generated invitation. Public profile data is unavailable until its owner completes and activates it. Header authentication actions lead to login/registration, and contact actions on service/route results lead to the corresponding public provider profile.

Supabase Auth owns credentials, email confirmation, sessions, and SMS MFA. FastAPI verifies Supabase JWTs and owns application-account, profile, invitation, and authorization APIs. The browser must not access application tables directly through Supabase Data API.

This work does not implement Didit, identity-document collection, a general chat system, payments, a company-owner-as-driver flow, or a new chat product. Didit verification is not required for account registration, profile completion, or activation in this design.

## 2. Approved roles and permissions

| Account role | Registration / relationship | Profile ownership and public visibility | Chat / company capabilities |
|---|---|---|---|
| Client | Registers directly with email/password and confirmed email; completes SMS MFA for login. | No provider profile is created by default. | Uses client features and participates in chats associated with their own service requests. |
| Company owner | Registers directly as a company owner; is not a driver. | Owns and manages one company profile; controls its completion, activation, and deactivation. | Can generate invitations for drivers linked to that company and access customer chats as the company representative. |
| Company-linked driver | No open driver signup. Joins through an invitation generated by the company owner and bound to that company. | Does not own the company profile and cannot edit or activate it. | No customer chat. Cannot invite drivers or change company ownership. |
| Independent driver | Registers directly as an independent driver. | Owns and manages their own independent-driver profile; no company RUT is collected or stored for this profile. | Has the approved driver chat capability. Cannot invite drivers or become a company-linked driver through the independent profile flow. |

Registration role is an allowlisted user selection, not an authorization claim. Company-linked driver role is assigned only by the server after a valid invitation is accepted. A user cannot submit a database role ID, company profile ID, account owner ID, activation timestamp, or driver affiliation and have it accepted as authoritative.

## 3. Authentication and registration flow

1. **Registration form:** `/registro` presents client, company owner, and independent driver choices. Company-linked drivers are directed to invitation acceptance, not an open role choice. The form collects only data required for the selected account/profile.
2. **Credentials:** the frontend calls Supabase Auth to create an email/password account. Email confirmation is required. Passwords are never stored in Amira tables or sent to FastAPI.
3. **Confirmation and sign-in:** the confirmation callback returns the user to the frontend. Login uses email/password first. An unconfirmed account cannot enter the authenticated application flow.
4. **SMS MFA:** after password authentication, the user must complete the configured SMS phone second factor before entering protected account/profile flows. Phone enrollment/verification must be established before relying on this factor. Supabase owns the factor and one-time code; Amira stores no SMS code.
5. **Application provisioning:** once the user has a confirmed, MFA-complete session, the frontend submits the role-specific application data to FastAPI. FastAPI verifies the bearer JWT, derives the Supabase user UUID (`sub`) and confirmed email from verified claims, validates the selected role against server-controlled roles, and creates the application rows transactionally. This operation must be idempotent so retrying after a network failure cannot create a second account/profile.
6. **Invitation acceptance:** a company owner creates an invitation addressed to a target email. The invitee confirms their email, authenticates, completes MFA, and accepts the single-use invitation. FastAPI matches the verified email to the invitation and creates a company-linked driver attached to the invited company; the client cannot choose or replace the company relationship.

The exact mechanism that carries role-specific registration data across email confirmation (for example, a frontend-held draft versus a server-side registration intent) is **unresolved**. Do not treat editable Supabase `user_metadata` as an authorization source. If used as a temporary draft transport, the backend must validate all submitted values and assign all protected fields itself.

### Role-specific form data

- **Client:** given name, family name, email/password, and a phone number for SMS MFA. Do not request a RUT unless a separately approved product requirement establishes its need.
- **Company owner:** account name/email/password/phone plus company profile display name and company RUT. Profile description, public location, logo, and service categories are profile content, not credentials. The owner is not inserted into `Conductor`.
- **Independent driver:** account name/email/password/phone plus the same public profile fields as a company (display name, description, location, logo, and services), but with profile kind “independent driver.” Do not collect or set company RUT. The driver has no invitation-management capability.
- **Company-linked driver:** invitation token, account name/email/password/phone. The invitation supplies the target company; the driver cannot provide an employer profile ID. Existing driver-type lookup is assigned/validated server-side; its canonical values need confirmation before implementation.

## 4. Profile lifecycle and public data

Use one adaptable public profile layout for company and independent-driver profiles. Its identity heading, descriptive content, location, logo, and service list come from a typed public-profile response; role-specific sections adapt to profile type without creating two unrelated page systems. Owner editing is private and distinct from the public view.

**Lifecycle:** draft/private → owner completes the required fields → owner activates → public. The owner may deactivate at any time; deactivation immediately removes the profile from public lookup and marketplace results. A company-linked driver cannot edit or activate the company profile. No identity-verification status or Didit result participates in these transitions.

**Activation completeness is not yet fully specified.** The design requires a server-side validation step before activation and does not equate non-null database columns with product completeness. Working assumption for implementation planning only: all profiles need a public display name and at least one public service offering; a company additionally needs its company RUT in private storage. Description, location, and logo remain optional unless the user approves stronger completeness criteria. An independent profile must have no company RUT. Confirm these exact criteria before coding.

**Allowlisted public fields:** profile ID, public profile kind (company or independent driver), display name, description, public location, logo URL, and offered service categories. A public response must never expose account email, phone, legal first/last name, company RUT, invite data/token, auth UUID, private vehicle identifiers, identity-verification records/status, or private storage keys. Public asset URLs must be access-controlled or deliberately public; do not return a storage key as a URL.

Existing `/api/services` and `/api/shared-routes` responses already use explicit response models, which is the pattern to extend. These endpoints currently do not filter on profile activation; adding activation filtering is required so an incomplete/deactivated profile cannot leak through search or route listings.

## 5. Proposed application and database design

The smallest coherent change keeps `Usuario`, `Perfil`, `Conductor`, and their existing lookup relationships, with these additions:

1. Add a stable machine-readable `code` to `Rol_Usuario` and `Rol_Perfil` with uniqueness, and seed the approved account/profile role values. Backend authorization uses these controlled codes, not labels or IDs supplied by the client. Exact migration/backfill values must be agreed with the existing seed/data state before implementation. Do not infer that `Tipo_Conductor` describes account permissions; its canonical semantics are not documented.
2. Add nullable `Perfil.public_activated_at` (or an equivalent explicitly named activation timestamp). Null means private; the API sets/clears it only after validating profile ownership and completeness.
3. Make `Conductor.employer_profile_id` nullable. A non-null value represents a company-linked driver; null represents an independent driver. Enforce through the service transaction that an independent driver owns an independent `Perfil`, while a company-linked driver has no separately owned driver profile and references a company profile. Existing `Perfil.owner_user_id` and `Conductor.user_id` uniqueness remain in force.
4. Add a `DriverInvitation` table with server-generated ID, company profile FK, normalized target email, token hash (never the raw token), creator user FK, created/expiry/accepted/revoked timestamps or equivalent state, and a unique token-hash constraint. It is single-use and scoped to the creator's company. **Invitation TTL is unresolved**; store expiry and enforce it, but do not invent the duration. Decide delivery mechanism and revocation UX separately.

Company RUT is currently nullable on `Perfil`, and the schema does not encode a profile-kind discriminator in a checkable column. Validate “company requires RUT; independent profile forbids RUT” in the typed FastAPI service/model boundary; a future DB-level conditional constraint requires an explicit profile-kind representation and should not be improvised. Keep normalized-email uniqueness, user/profile uniqueness, and driver uniqueness. Update model structural tests and expected table inventories when the invitation table is introduced.

The current public-browse migration enables RLS and revokes Data API privileges from `PUBLIC`, `anon`, and `authenticated` for application tables. Preserve that default-deny posture and include the new invitation table in the same RLS/revoke coverage. FastAPI is the application data-access boundary; do not grant browser roles direct table access to simplify the frontend.

System-assigned fields include all row IDs and timestamps; `Usuario.auth_user_id` from verified JWT `sub`; `Usuario.email` from verified confirmed identity; `role_id` from the server's role-code lookup; `Perfil.owner_user_id` from the authenticated actor; `Perfil.role_id` and activation timestamp from validated server logic; `Conductor.user_id`, `employer_profile_id`, and `driver_type_id` from actor/invitation plus controlled lookup; and all invitation creator/profile/hash/state/expiry/acceptance fields. The API must ignore or reject client-supplied values for these fields.

## 6. API responsibilities

The exact path names are proposals; keep contracts explicit and versioned consistently with existing `/api` routes.

- `POST /api/accounts/registration`: authenticated, confirmed, MFA-complete; accepts a role-specific payload; derives identity from JWT; validates allowlisted role; creates `Usuario` and any profile/driver row in one transaction; idempotent by Auth UUID.
- `GET /api/accounts/me`: returns the caller's own account role and onboarding/profile state only.
- `GET/PATCH /api/profiles/me`: read/update only the caller-owned company or independent profile; typed writable-field allowlist; never allow the company-linked driver to mutate company profile fields.
- `POST /api/profiles/me/activate` and `POST /api/profiles/me/deactivate`: owner-only lifecycle operations with server-side completion checks and audit timestamps.
- `GET /api/public/profiles/{profile_id}`: unauthenticated allowlisted DTO for active profiles only; inactive, missing, or unknown IDs return the same not-found behavior.
- `POST /api/company/profiles/me/driver-invitations`: company-owner-only; creates a target-email-bound invite. `POST /api/driver-invitations/{token}/accept`: authenticated/MFA-complete user; verifies token hash, expiry, unused state, email match, company role, and account role before single-transaction acceptance.
- Existing public service/route list endpoints: filter out private/inactive profiles and continue returning only explicit response schemas.
- `PublicSharedRoute` needs a `profileId` from its associated `Viaje.profile_id` so the frontend can link its contact action to the provider profile. `PublicServiceItem` already carries `profileId`; reuse it for the service contact action.

FastAPI needs a shared authentication dependency that verifies JWT signature, issuer, audience, expiry, and subject against the configured Supabase issuer/key material; existing `Settings` has issuer/audience settings but no current auth dependency is present. Authorization checks must use verified claims plus server-loaded application records. Never authorize from user-editable Supabase `user_metadata`. Existing chat endpoints/tables are outside implementation scope, but any later chat API must check chat participation and role policy server-side on reads and writes; company owners and independent drivers may access their customer chats, while company-linked drivers must be denied. This section sets a policy boundary, not a new chat implementation.

## 7. Frontend routes and components

- `/login`: email/password form, then mandatory SMS code challenge; clear pending/confirmed/MFA/error states.
- `/registro`: role selection excluding company-linked driver, role-specific data, email confirmation handoff.
- `/auth/callback`: validates the Supabase confirmation return and resumes sign-in/onboarding without accepting arbitrary redirect URLs.
- `/auth/mfa`: phone enrollment/challenge and code verification as required by the Auth state.
- `/invitacion/conductor/[token]`: invitation context and company name, sign-in/signup as needed, then acceptance. Do not display or place raw invitation tokens in logs or analytics.
- `/cuenta/perfil`: private owner profile editor/status for company owner or independent driver; company-linked drivers receive only their own account details, not owner controls.
- `/prestadores/[profileId]`: public profile using the shared adaptable layout; inactive profiles resolve as not found.
- The home header's sign-in action routes to `/login`, and its provider-registration CTA routes to `/registro`. `MarketplaceHeader` exposes the same login/registration actions in desktop and mobile navigation.
- Service and shared-route result cards include a contact action linked to `/prestadores/[profileId]`; the action opens the public profile rather than creating a chat directly.

Reuse the current Next.js App Router, Supabase SSR browser/server helpers, existing marketplace header/footer and responsive custom CSS conventions. Update navigation to link login/register and provider profiles. Frontend guards improve navigation only; FastAPI remains the access-control authority. Use server/client-safe session handling already established by `@supabase/ssr`; do not expose service-role/secret keys. Keep redirect destinations allowlisted and avoid putting tokens or personal data in query strings.

## 8. Error and security behavior

- Require email confirmation; block incomplete sign-in and show actionable confirmation/resend UI without revealing whether an arbitrary address has an account.
- Do not issue an authenticated application session for protected flows until the SMS MFA step completes. Invalid/expired codes, missing phone factor, and factor enrollment/recovery failures fail closed; exact recovery and factor replacement policy remains an open decision.
- Use generic login/registration messages that avoid account enumeration; rate-limit password attempts, MFA challenges, invitation creation, and invitation acceptance.
- Validate form input client-side for usability and repeat all validation server-side. Bound field lengths, normalize email consistently, and avoid logging passwords, OTPs, raw invite tokens, JWTs, or private profile data.
- Check profile ownership, role, invitation company scope, invitee email, expiry, and single-use status on every protected mutation. Use database transactions and uniqueness constraints to prevent concurrent invite acceptance or duplicate provisioning.
- Browser sends only a publishable Supabase key. FastAPI verifies bearer tokens; no secret/service-role key reaches `NEXT_PUBLIC_*` variables. Preserve current RLS/Data API default-deny configuration.
- Public endpoint DTOs are explicit allowlists. Never serialize ORM models directly. Do not use UUID obscurity as authorization.
- Didit or identity verification must not be called, required, or used to gate the approved flows.

## 9. Acceptance criteria and planned checks

1. Each of the three direct signup roles can create only its permitted account/profile shape after email confirmation and SMS MFA; linked drivers cannot open-register.
2. A company owner cannot create a `Conductor` row for themselves through owner signup. Independent drivers get a driver row with no employer profile and a separately owned independent profile; company RUT is absent. Company-linked drivers can be provisioned only by accepting an unexpired owner-created invite and are linked to that owner’s company profile.
3. Replayed, expired, revoked, wrong-email, wrong-company, or concurrent invite acceptance cannot create/reattach a driver. Independent drivers and company-linked drivers cannot create invitations.
4. Profile API updates and activation are owner-scoped. Incomplete and deactivated profiles are absent from public profile, service, and route results; activated profiles use the same layout for both kinds.
5. Public DTO tests prove no email, phone, legal name, RUT, auth ID, invite/token, verification state, or storage key escapes. Company-linked drivers cannot access owner profile mutation or customer-chat capability; company owners and independent drivers retain the approved chat capability at the authorization-policy boundary.
6. Invalid JWT signature/issuer/audience/expiry, missing MFA-complete assurance, and unauthenticated access to private APIs fail closed. Role claims in editable user metadata do not grant privileges.
7. Automated checks should include SQLAlchemy structural/model tests (including nullable employer FK and invitation uniqueness), migration/RLS inventory tests, FastAPI auth/authorization and public-schema tests, and Playwright flows for confirmation, MFA, role-specific forms, invite acceptance, activation visibility, error states, responsive layout, and keyboard/accessibility behavior. Existing frontend Playwright coverage is marketplace/home-focused and has no auth flows. No tests or services were run for this design-only task.
8. Desktop and mobile header authentication actions navigate to `/login` and `/registro`; all links lead to implemented routes without 404s.
9. Service and shared-route contact actions navigate to the correct active provider profile. Shared-route API responses include the profile identifier needed for the link, and missing/inactive profiles do not produce a dead CTA.

## 10. Assumptions and decisions still needed

- **Confirmed:** the four account cases and capability rules in Section 2; company owners and independent drivers can access customer chats while linked drivers cannot; email/password with required confirmation; password then SMS phone MFA; one shared adaptable public profile layout; Supabase Auth credential ownership; FastAPI JWT verification and application/profile/invite API ownership; profile activation gating; Didit not required now.
- **Working assumption:** one account role per account, consistent with singular `Usuario.role_id`. Supporting a client who also owns a company would need explicit multi-role policy/schema design.
- **Open:** invitation token TTL, invitation delivery channel, resend/revoke behavior, and whether invitees must already be registered.
- **Open:** exact profile-completion fields and whether service offering must be configured before activation. The proposal in Section 4 is a planning assumption, not user approval.
- **Open:** SMS factor enrollment timing, phone change/recovery policy, and exact assurance claim/API support; verify current Supabase configuration/docs during implementation (no remote access was used for this design).
- **Open:** canonical lookup role/driver-type seed values and a safe migration/backfill path for existing rows. Current docs say role tokens are not canonicalized.
- **Open:** which profile fields are editable by whom after activation, public location precision, logo storage/URL policy, and whether a user may later change account role. Until resolved, preserve profile ownership and use an explicit allowlist.
- **Open:** registration-data transport across the email-confirmation interruption and password reset/session invalidation behavior.
