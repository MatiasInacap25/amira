# Admin Panel

Objective: an administrator area (`/admin`) with a sidebar of every manageable entity and a content area that changes with the selected option, backed by `/api/admin/*` endpoints. Demo target for the final presentation, sandbox only.
Branch: `feat/admin-panel` from `develop`, worktree `/mnt/data/projects/amira-worktrees/admin-panel`. Delivery: `ask-on-risk`. Test runners: backend `uv run pytest`; frontend `node --test tests/unit/*.mjs` and `npx playwright test`.
Implementer: Codex (delegated through herdr). Requirements source: `docs/requisitos/modelo-b-lo-que-falta.md` (rows 65a–65e, 38, 22, 24, 9).

## Specs

### S0. Business decisions already made (do not change)

- Tax model is **mandato**: the carrier sells the freight; Amira only earns a commission and invoices that commission to the carrier.
- Quotations **include IVA 19 %**. A quote of 80.000 means the customer pays 80.000 (neto 67.227 + IVA 12.773).
- Commission stays as the code computes it today: `commission_for(gross, payout_commission_percent)` (10 % of the gross payment, whole CLP, half up). For 80.000 → commission 8.000, carrier receives 72.000.
- IVA of a commission is extracted, not added: `commission_net = round_half_up(commission / 1.19)`, `commission_iva = commission - commission_net`. 8.000 → net 6.723, IVA 1.277.
- Amira's IVA débito shown in the panel is **only the IVA of commissions** (and of retained cancellation amounts, which are platform income). Never show the IVA of the whole freight as Amira's.
- Sandbox only: every money action uses the existing simulated adapters (`simulated_payment_provider.py`, `simulated_payout_provider.py`) and their fail-closed `APP_ENV` rule. Do not add a real provider.

### S1. Access control

- New setting `admin_user_ids` in `backend/src/amira_api/settings.py`, env var `ADMIN_USER_IDS`: comma-separated Supabase user UUIDs (the JWT `sub`). Empty by default → nobody is admin. Add it to `backend/.env.example` with a comment.
- `backend/src/amira_api/admin/deps.py`: `require_admin` dependency = `get_current_user` (reuse the existing assurance boundary in `auth.py`, do not reimplement JWT checks) + `current_user.id in settings.admin_user_ids`. No token → 401 (existing behavior). Valid user not in the list → 403 `{"detail": "Admin access required."}`.
- Every `/api/admin/*` route depends on `require_admin`. No admin route is reachable without it (add a test that iterates the router's routes and asserts the dependency is present).
- Frontend: `/admin` and all sub-routes check access server-side before rendering (call `GET /api/admin/me`; on 401 redirect to `/login?next=/admin`; on 403 render "No tienes acceso al panel de administración." with a link to `/`). Never decide admin access in the browser only.
- `GET /api/admin/me` → `{ "user_id", "email" }`, used by the layout header.
- Admins are not managed from the UI in this iteration (see S25).

### S2. Layout

Reference: user's sketch — sidebar on the left with the options, content/dashboard on the right.

- Route group `frontend/src/app/admin/` with a shared `layout.tsx`: fixed left sidebar (240 px) + scrollable content area. Each sidebar option is its own route (`/admin`, `/admin/clientes`, `/admin/conductores`, ...), so the URL reflects the selected option and the browser back button works.
- Sidebar: Amira logo + "Admin" label at the top; grouped options (groups below) with an icon each (lucide-react, already in the project); active option highlighted; a count badge on options with pending work (documents in review, open claims, bank accounts pending, payouts due). Footer: admin email + "Cerrar sesión".
- Sidebar groups and order:
  - **General**: Principal
  - **Personas**: Clientes, Proveedores, Conductores, Invitaciones
  - **Revisión**: Documentos de conductores, Cuentas bancarias, Reclamos, Valoraciones
  - **Operación**: Solicitudes, Cotizaciones, Servicios, Rutas compartidas, Vehículos, Chats
  - **Finanzas**: Pagos, Reembolsos y cancelaciones, Desembolsos, Comisiones e IVA
  - **Sistema**: Catálogos, Auditoría, Configuración
- Below 1024 px the sidebar collapses into a drawer opened by a menu button in a top bar. No horizontal page scroll; tables scroll horizontally inside their own container.
- Content area header: page title, one-line description, and the page's primary action button when it has one (e.g. "Crear tipo de servicio").
- UI copy in Spanish, code identifiers in English (project convention). Reuse the existing design tokens/styles in `globals.css` / `src/styles/lp-app.css`; do not add a UI library.

### S3. Common table pattern (applies to every list page unless a page says otherwise)

- Toolbar: free-text search box (debounced 300 ms, searches the columns listed per page), filter controls listed per page, "Limpiar filtros" button, and "Exportar CSV" (exports the current filtered set, max 5.000 rows, generated by the backend at `GET /api/admin/<entity>/export.csv` with the same query params).
- Filters and search live in the URL query string, so a filtered view can be shared and survives reload.
- Columns are sortable where marked (sort param `sort=<field>` / `sort=-<field>`); default sort is newest first.
- Server-side pagination: `limit` (default 20, max 100) + `offset`; response `{ items, total, limit, offset }` (same shape as the existing public pages). Pagination controls show "Mostrando X–Y de Z".
- Last column: a "⋮" button that opens a menu with the row actions listed per page. Actions not allowed for the row's current state are shown disabled with a tooltip explaining why (e.g. "Solo se puede reembolsar un pago aprobado").
- Clicking a row (outside the ⋮ menu) opens the **detail view** for that row in a right-side panel (drawer, 480 px) with all fields listed per page and related links.
- States: skeleton while loading, empty state ("No hay resultados con estos filtros"), error state with "Reintentar".
- Money in CLP formatted `$80.000`; dates in `America/Santiago` as `dd-mm-aaaa HH:mm`; RUT formatted `12.345.678-9`; status values shown as colored badges with Spanish labels.
- Destructive or state-changing actions open a confirmation dialog that names the target and the consequence. Reject/suspend/cancel/refund/resolve actions require a **mandatory reason** (textarea, 10–500 chars).
- After an action: toast with the result, the row refreshes in place, the sidebar badges refresh.
- Every state-changing admin action writes one row to the audit log (S24) in the same DB transaction as the change.

### S4. Principal (dashboard) — `/admin`

- Period filter: Hoy, 7 días, 30 días (default), Mes actual, Rango personalizado.
- KPI cards (for the selected period):
  1. Recaudado: sum of approved `Pago` amounts.
  2. Reembolsado: sum of `Reembolso` amounts.
  3. Recaudado neto: 1 − 2.
  4. Por pagar a transportistas: sum of the net amount owed for services that are `completed`, have an approved payment and no `Desembolso` (the same rule as `payout_service._due_service_ids`, reused, not duplicated). Sub-line: "N servicios, M bloqueados por reclamo".
  5. Pagado a transportistas: sum of `Desembolso.net_amount`.
  6. Comisiones: gross, net and IVA per S0.
  7. IVA débito de Amira: commission IVA + IVA of retained cancellation amounts.
  8. Servicios en curso (`in_progress`), Servicios completados, Servicios cancelados.
  9. Pendientes de revisión: documentos de conductores `in_review`, reclamos abiertos, cuentas bancarias pendientes. Each card links to its page with the filter pre-applied.
- Chart: daily recaudado vs comisiones for the period (simple bar/line chart; use an existing dependency if present, otherwise inline SVG — do not add a heavy chart library).
- Table "Últimos movimientos" (10 rows, no pagination): date, type (Pago, Reembolso, Desembolso), service ID (link to the service detail), customer, provider, amount, status.
- Endpoint: `GET /api/admin/finance/summary?from=&to=` + `GET /api/admin/finance/timeseries?from=&to=&bucket=day` + `GET /api/admin/finance/movements?limit=10`.

### S5. Clientes — `/admin/clientes`

Entity: `Usuario` with role code `client`.

- Columns: nombre completo, RUT, correo, teléfono, fecha de registro (sortable), N° servicios, total pagado (sortable), estado (Activo / Bloqueado).
- Search: nombre, RUT, correo. Filters: estado, fecha de registro (rango), "con reclamos".
- ⋮ menu: Ver detalle · Editar datos de contacto · Bloquear (reason) / Desbloquear · Ver servicios (→ `/admin/servicios?customer=<id>`) · Ver pagos (→ `/admin/pagos?customer=<id>`).
- Detail: datos personales, fecha de registro, verificación (assurance/MFA), resumen (servicios por estado, total pagado, reembolsado, reclamos), últimos 5 servicios.
- CRUD: no create (customers self-register through Supabase); update limited to nombre, apellido and teléfono (RUT and correo are read-only: RUT is a unique identity, correo belongs to Supabase Auth); no hard delete — "Bloquear" is the soft delete.
- Blocked user: every non-admin authenticated endpoint returns 403 `{"detail": "Tu cuenta está bloqueada. Contacta a soporte."}`. Implement the check once in the shared auth path, not per router. Requires a new nullable column (S26).

### S6. Proveedores — `/admin/proveedores`

Entity: `Perfil` (`kind` = `company` or `independent_driver`).

- Columns: nombre / razón social, tipo (Empresa / Conductor independiente), RUT empresa, dueño (nombre + correo), publicado (`public_activated_at` set or not), N° conductores, N° vehículos, servicios completados, calificación promedio, estado (Activo / Suspendido).
- Search: nombre, RUT, correo del dueño. Filters: tipo, publicado, estado, región de operación if available.
- ⋮ menu: Ver detalle · Ver perfil público (opens `/prestadores/<id>` in a new tab) · Despublicar (reason) / Volver a publicar (only if it still meets the existing `_missing_items` rule) · Suspender (reason) / Reactivar · Ver conductores · Ver vehículos · Ver servicios · Ver cuenta bancaria.
- Detail: datos del perfil, dueño, servicios ofrecidos (`ServicioDisponible`), conductores, vehículos, cuenta bancaria (S10), desembolsos recibidos, reclamos en su contra, valoraciones.
- CRUD: no create (providers onboard themselves); edit limited to the public descriptive fields the provider can already edit; no delete — "Suspender" is the soft delete.
- Suspended profile: hidden from public browse and shared routes, cannot quote, publish trips, or accept requests (409 `{"detail": "El perfil está suspendido."}`). Services already confirmed are not cancelled automatically; the detail warns how many are open. Requires a new column (S26).

### S7. Conductores — `/admin/conductores`

Entity: `Conductor` + its `Usuario` + `TipoConductor`.

- Columns: nombre, RUT, correo, tipo (de empresa / independiente), perfil/empresa (link), verificación (Verificado / En revisión / Rechazado / Sin documento), servicios asignados, último servicio, estado.
- Search: nombre, RUT, correo. Filters: tipo, empresa, estado de verificación.
- ⋮ menu: Ver detalle · Ver documento de verificación (→ S9 filtered) · Bloquear (reason) / Desbloquear (blocks the underlying `Usuario`, S5 rule) · Ver servicios asignados.
- Detail: datos personales, empresa, historial de verificaciones (`VerificacionIdentidad`, newest first), asignaciones (`ServicioAsignacion`) with vehicle and service.
- CRUD: no create (drivers join via invitation or self-onboarding); read + block only.

### S8. Invitaciones — `/admin/invitaciones`

Entity: `DriverInvitation` (+ attempts).

- Columns: correo invitado, empresa, enviada, expira, estado (pendiente, aceptada, expirada, revocada — use the values the code already defines), intentos.
- Filters: estado, empresa. Search: correo.
- ⋮ menu: Ver detalle · Revocar (only pending; reason).
- Read-only otherwise.

### S9. Documentos de conductores — `/admin/documentos`

Entity: `VerificacionIdentidad` (driver certificates; statuses `verified`, `in_review`, `rejected`).

- Default filter: estado = En revisión. Sidebar badge = count `in_review`.
- Columns: conductor, RUT, empresa, tipo de documento, subido, resultado automático (Verifik), estado, revisado por, revisado el.
- Filters: estado, fecha de subida. Search: conductor, RUT.
- ⋮ menu: Ver documento · Aprobar · Rechazar (reason).
- Detail / review view: the PDF rendered inline through a short-lived signed URL (reuse `supabase_evidence_storage.py`, as the existing review CLI does), the automatic verification result and annotations side by side, and two buttons "Aprobar" / "Rechazar" (reason). Keyboard: next pending document after a decision.
- Approve/reject reuses the same domain function the existing review CLI uses (find it; do not write a second implementation). Only `in_review` rows can be decided; deciding twice → 409.

### S10. Cuentas bancarias — `/admin/cuentas-bancarias`

Entity: `CuentaDesembolso` (`registration_status`).

- Columns: proveedor, banco, tipo de cuenta, número (masked `****1234`), RUT titular, RUT del perfil, coincide (✔ / ✖), estado de registro, creada.
- Filters: estado, coincide. Search: proveedor, RUT.
- ⋮ menu: Ver detalle · Aprobar (disabled when RUT titular ≠ RUT del perfil, tooltip "El RUT del titular no coincide con el del proveedor") · Rechazar (reason) · Deshabilitar (reason).
- Only an approved account can receive payouts; this matches `payout_service`'s `missing_account` check. If the existing model has no field for titular RUT, bank, type or number, add them as nullable columns (S26) and show "Sin dato" when null.

### S11. Reclamos — `/admin/reclamos`

Entity: `Reclamo` (service goes to `disputed` and blocks the payout).

- Default filter: abiertos. Sidebar badge = open count.
- Columns: N° reclamo, servicio (link), cliente, proveedor, motivo, creado, días abierto (sortable), monto en juego, estado.
- Filters: estado, fecha, proveedor. Search: cliente, proveedor, servicio ID.
- ⋮ menu: Ver detalle · Resolver a favor del cliente (reason) · Resolver a favor del proveedor (reason) · Ver chat del servicio.
- Detail: claim text, customer evidence (signed URLs), delivery photo of the service, service timeline, payment and payout state, the service chat (read-only, S16).
- Resolution rules (new function in a service module, e.g. `admin/claim_service.py`, under a row lock on the service, idempotent, audited):
  - **A favor del cliente**: full refund through the existing refund path with the simulated provider (creates `Reembolso`), service → `cancelled`, no payout is ever released for it.
  - **A favor del proveedor**: service → `completed`, claim closed; the service becomes due for payout under the normal `payout_service` rules.
  - Resolving a claim that is not open → 409. Store resolution, reason, admin ID and timestamp (S26).

### S12. Valoraciones — `/admin/valoraciones`

Entity: `Valoracion`.

- Columns: proveedor, cliente, servicio, nota (1–5), comentario (truncated), fecha, visible.
- Filters: nota, visible, proveedor. Search: comentario, proveedor.
- ⋮ menu: Ver detalle · Ocultar (reason) / Mostrar.
- Hidden ratings are excluded from public pages and from the provider's average. No edit, no hard delete. Requires a new column (S26).

### S13. Solicitudes — `/admin/solicitudes`

Entity: `FormularioServicio` (statuses `pending`, `accepted`, `rejected`).

- Columns: N°, cliente, proveedor, tipo de servicio, origen → destino (comunas), fecha solicitada, estado, N° cotizaciones, creada.
- Filters: estado, tipo de servicio, fecha, región. Search: cliente, proveedor, origen, destino.
- ⋮ menu: Ver detalle · Ver cotizaciones · Ver chat.
- Detail: all form fields (description, weight, volume, addresses, exclusivity), images (`ImagenFormulario`, signed URLs), quotes.
- Read-only.

### S14. Cotizaciones — `/admin/cotizaciones`

Entity: `Cotizacion` (statuses `pending`, `paid`, `rejected`, `expired`, `superseded`).

- Columns: N°, solicitud (link), proveedor, cliente, monto total (IVA incluido), neto, IVA, comisión estimada, estado, válida hasta, creada.
- Filters: estado, proveedor, rango de monto, fecha. Search: proveedor, cliente.
- ⋮ menu: Ver detalle · Ver solicitud · Ver pago (if `paid`).
- Read-only. The neto/IVA/commission columns are computed with the S0 rules; nothing is stored.

### S15. Servicios — `/admin/servicios`

Entity: `Servicio` (statuses `confirmed`, `in_progress`, `completed`, `disputed`, `cancelled`).

- Columns: N°, cliente, proveedor, conductor(es), vehículo(s), origen → destino, inicio, fin, monto, estado, pago, desembolso, exclusivo/compartido.
- Filters: estado, proveedor, cliente, fecha (rango), exclusivo, "con reclamo", "listo para desembolso". Search: N°, cliente, proveedor, patente.
- ⋮ menu: Ver detalle · Ver ubicación en vivo (only `in_progress`) · Cancelar (reason; only `confirmed`; uses the existing `cancel_service` and its refund/retention rules) · Ver pago · Ver desembolso · Ver chat · Ver reclamo.
- Detail: timeline (created, paid, assigned, started, completed / cancelled / disputed, payout), assignments, last known location (`ServicioUbicacion`), delivery photo, money breakdown (total, neto, IVA, commission, carrier net — S0), linked trip and stops if shared.
- No create, no edit of business fields, no delete: services come from paid quotes.

### S16. Chats — `/admin/chats`

Entity: `Chat`, `ChatParticipante`, `Mensaje`.

- Privacy rule: admins can only open chats linked to a service that has a claim, or when they enter a reason (logged in the audit log as "chat access"). The list shows metadata only (participants, service, last message date, message count), never message text.
- Detail: read-only transcript with attachments (signed URLs). No sending, editing or deleting messages.

### S17. Rutas compartidas — `/admin/rutas-compartidas`

Entity: `Viaje` + `ViajeVehiculo` + `ParadaViaje`.

- Columns: N°, proveedor, origen → destino (regiones), salida, estado, publicado, acepta solicitudes, N° servicios unidos, N° paradas.
- Filters: estado, publicado, acepta solicitudes, fecha de salida. Search: proveedor.
- ⋮ menu: Ver detalle · Despublicar (reason) · Cerrar a nuevas solicitudes (reuse `close_shared_trip`) · Ver en el sitio público.
- Detail: vehicle and driver, ordered stops (with their real role: origen, retiro de <cliente>, entrega de <cliente>, destino), linked services.

### S18. Vehículos — `/admin/vehiculos`

Entity: `Vehiculo`.

- Columns: patente, proveedor, tipo/marca/modelo if available, peso máximo, servicios realizados, creado, estado.
- Filters: proveedor, estado. Search: patente.
- ⋮ menu: Ver detalle · Editar · Deshabilitar (reason) / Habilitar.
- CRUD: no create (providers register vehicles); edit limited to non-identity fields (patente is unique identity → read-only); "Deshabilitar" is the soft delete and prevents assigning the vehicle to new services (409). Requires a new column if none exists (S26).

### S19. Pagos — `/admin/pagos`

Entity: `Pago` + `PaymentProviderTransaction`.

- Columns: N°, servicio/cotización, cliente, proveedor, monto, neto, IVA, estado (use the existing payment status values), proveedor de pago (Mercado Pago / simulado), ID externo, creado, aprobado.
- Filters: estado, fecha, rango de monto, proveedor de pago. Search: N°, ID externo, cliente.
- ⋮ menu: Ver detalle · Ver transacciones del proveedor · Ver servicio · Reembolsar (reason; only approved payments whose service is not completed-and-paid-out; goes through the existing cancellation/refund domain path, never by editing `Pago` directly).
- Detail: every provider transaction (status, amounts, `live_mode`, raw status detail), refunds.

### S20. Reembolsos y cancelaciones — `/admin/reembolsos`

Entity: `Reembolso`.

- Columns: N°, pago, servicio, cliente, monto devuelto, monto retenido (platform income), motivo, iniciado por (cliente / proveedor / admin), fecha, estado.
- Filters: iniciado por, fecha. Search: cliente, servicio.
- ⋮ menu: Ver detalle · Ver pago · Ver servicio. Read-only (refunds are created from S11, S15 or S19).

### S21. Desembolsos — `/admin/desembolsos`

Entity: `Desembolso`.

- Two tabs:
  - **Pendientes**: services due for payout (same rule as the dashboard card 4), with columns servicio, proveedor, cuenta bancaria (estado), bruto, comisión, neto a pagar, completado el, bloqueado por (reclamo / sin cuenta aprobada / plazo de reclamo vigente). Toolbar action "Liberar desembolsos vencidos" calls the existing `release_due_payouts` with the simulated provider and shows the returned summary (due, released, skipped by reason). Confirmation required.
  - **Pagados**: columns N°, servicio, proveedor, bruto, comisión, neto, ID del proveedor de pago, liberado el, estado.
- Filters: proveedor, fecha. Search: proveedor, servicio.
- ⋮ menu: Ver detalle · Ver servicio · Descargar comprobante (simple HTML/PDF receipt generated on the fly with the S0 breakdown).

### S22. Comisiones e IVA — `/admin/finanzas`

- Period filter (month picker, default current month) and a table by month: comisiones brutas, comisiones netas, IVA de comisiones, retenciones por cancelación (neto + IVA), IVA débito total. Footer note: "Base de cálculo para el F29. Validar con el contador."
- Second table: comisión por proveedor in the period (proveedor, N° servicios, bruto cobrado, comisión, IVA de la comisión, neto pagado).
- "Exportar CSV" per S3. Read-only.

### S23. Catálogos — `/admin/catalogos`

Tabs:
- **Tipos de servicio** (`TipoServicio`): full CRUD — create, edit name/description, deactivate. Hard delete only when no `ServicioDisponible` or `FormularioServicio` references it; otherwise only deactivate (409 with explanation).
- **Tipos de conductor** (`TipoConductor`): read-only (code relies on fixed codes).
- **Regiones y comunas** (`Region`, `Commune`): read-only, searchable.
- **Roles** (`RolUsuario`, `RolPerfil`): read-only.

### S24. Auditoría — `/admin/auditoria`

- New table `admin_audit_log` (S26): id, admin user ID, action code, entity type, entity ID, reason, before/after JSON snapshot of the changed fields, created_at. Insert-only (no update/delete endpoints).
- Columns: fecha, admin, acción, entidad (link), motivo. Filters: admin, acción, entidad, fecha. Read-only.

### S25. Configuración — `/admin/configuracion`

- Read-only view of: commission percent, APP_ENV, which payment and payout adapters are active (simulated / Mercado Pago sandbox), admin user list from `ADMIN_USER_IDS` (resolved to emails), claim window hours. No editing from the UI.

### S26. Data changes allowed

Additive Alembic migrations only (new tables, new nullable columns, new indexes). No changes or deletes of existing rows, no column renames/drops. Spanish DB names, English Python names (project convention). RLS enabled and privileges revoked from `anon`/`authenticated` on every new table, like the existing migrations. Expected additions:
- `Usuario`: `blocked_at`, `blocked_reason`.
- `Perfil`: `suspended_at`, `suspended_reason`.
- `Vehiculo`: `disabled_at`, `disabled_reason` (if no equivalent exists).
- `Valoracion`: `hidden_at`, `hidden_reason`.
- `Reclamo`: `resolution` (`customer` / `provider`), `resolved_at`, `resolved_by`, `resolution_reason` (if not present).
- `CuentaDesembolso`: titular RUT, bank, account type, account number (if not present).
- New `admin_audit_log`.

### S27. Backend structure

- Package `backend/src/amira_api/admin/`: `__init__.py`, `deps.py`, `schemas.py`, one `<entity>_routes.py` per section (or grouped by sidebar group), service modules for state-changing actions (`claim_service.py`, `moderation_service.py`, ...), `audit.py`, `csv_export.py`. One router aggregator `admin/router.py` mounted in `main.py` with prefix `/api/admin`.
- Routers stay thin; business rules in service modules; reuse existing domain functions (`cancel_service`, `release_due_payouts`, `commission_for`, `_missing_items`, `close_shared_trip`, the driver-certificate review function). Never duplicate a business rule.
- Authorization is enforced in endpoints (privileged DB connection bypasses RLS — see root `CLAUDE.md`).

### S28. Frontend structure

- `frontend/src/app/admin/` (`layout.tsx`, `page.tsx`, one folder per section), `frontend/src/components/admin/` (Sidebar, DataTable, RowActionsMenu, DetailDrawer, ConfirmDialog, ReasonDialog, StatusBadge, KpiCard, Filters), `frontend/src/lib/admin/` (API client, formatters, query-string ⇄ filter mapping).
- Read the relevant guide in `frontend/node_modules/next/dist/docs/` before writing Next.js code (this Next version has breaking changes; `src/proxy.ts` replaces middleware).
- Browser talks only to FastAPI (`NEXT_PUBLIC_API_URL`), never to the database.

### S29. Tests and checks

- Backend (`backend/tests/admin/`): 401 without token, 403 for non-admin, 200 for admin on every route; each state-changing action: happy path, invalid state → 409, audit row written, reason required; dashboard sums with known fixtures (including the 80.000 → 8.000 / 6.723 / 1.277 example); blocked user gets 403 on a normal endpoint; suspended profile hidden from public browse.
- Frontend: node unit tests for formatters (CLP, RUT, IVA extraction) and filter ⇄ query-string mapping; Playwright spec for the admin layout (sidebar navigation changes content and URL, non-admin sees the no-access message, a reject-with-reason flow).
- Must pass: `uv run pytest`, `uv lock --check`, `npm run lint`, `npm run build`, `node --test tests/unit/*.mjs`, `npx playwright test`.
